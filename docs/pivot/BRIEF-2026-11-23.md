# Kosta's product pivot, 2026-11-23 (verbatim brief, condensed only where marked)

Make kabl much easier to start using, much easier to learn, much easier to understand and reuse,
and available to Windows musicians through VST3, without sacrificing musical depth and modular identity.

## A. First-run experience
A new user should quickly: get a useful sound; understand how to play it; find and load other sounds;
make a meaningful change to a sound; understand what that change does; discover what to do next.
Current first run is a starting point. Standalone (audio device + MIDI setup) and plugin (inside a host)
may differ, but avoid two unrelated onboarding systems. No forced tutorial; never in the way of normal use.

## B. Learning path (part of the original vision; a real product feature)
Not more help text, isolated tooltips or disconnected tutorial pages. Progressive, practical, teaches kabl
and modular synthesis through interaction with real patches and sounds. Proposed progression (refine it):
1 Find and play sounds (browse, preview, load, play, save variations)
2 Change sounds (macros, exposed controls, how a musical control maps to underlying params)
3 Signal flow (inspect modules, follow connections, how sound is produced/processed)
4 Build a voice (oscillators, envelopes, VCAs, filters, ...)
5 Movement (sequencing, modulation, clocks, timing)
6 Perform (macros, scenes/cues, performance controls)
7 Reusable modules (encapsulate, expose controls and ports, reuse)
8 kabl in a DAW (plugin use, MIDI, automation, production workflows)
Principles: doing and listening over reading; real patches and real app functionality; lessons end in
useful editable results; optional, revisitable, non-intrusive; never lock functionality behind lessons;
explain what controls change in the current patch; allow inspecting the real structure (no fake abstraction).
One coherent learning system for the whole progression, not bespoke UI per lesson.

## C. Corpus-wide modularization and legibility (major priority)
Complex patches (e.g. Lichen) are too visually complicated flat. NOT: simplify Lichen by hand.
IS: audit the ENTIRE corpus, discover recurring structures, build a coherent library of reusable musical
building blocks (composites).
Corpus: factory presets, Voices, FX, Pieces/compositions, examples/demos, promo patches, other user-facing
playable assets. Classify fixtures/dev-only assets separately. Not a few representative patches.
Per candidate: how many / which patches; genuinely equivalent vs superficially similar; musical purpose;
params to expose; ports to expose; public interface; visible complexity removed; useful standalone too.
No arbitrary grouping to cut module counts; a composite must be a coherent useful musical component.
Interfaces: musically meaningful control names, useful defaults/ranges/units, clear explanations, right
underlying params exposed without overwhelming, meaningful audio/mod/clock/gate/trigger ports, custom panel
where useful, internal graph openable. Build on existing D09/D10 composite + panel infrastructure; extend only
for real gaps.
Order: complete corpus manifest + ranked candidate catalogue -> pick small high-value set -> implement
definitions/interfaces -> test standalone and in parents -> refactor representative patches -> verify sound,
routing, sequencing, automation, state, compatibility -> evaluate rack layouts/panels -> expand on evidence.
Lichen is a major validation case, not the sole basis. Some structures stay bespoke.
Preserve behaviour: params, routing, modulation, timing, sequencing, cue refs, MIDI mappings, host
automation, saved state. Exact render comparisons where possible. Any intentional sonic change is a product
decision for Kosta. Keep composite snapshot + compatibility semantics.

## D. Windows and VST3
Linux standalone + CLAP stay first-class. Add Windows standalone + Windows VST3. macOS/AU deferred.
Same engine and patch model. Prove the best VST3 route from the existing plugin; wrapper approach is the
preferred hypothesis, validate it. Areas: Windows audio/MIDI, filesystem/config paths, user libraries/presets,
GUI/windowing backend, DPI/resizing, editor lifecycle, VST3 install/discovery, host state recall, host
automation with stable param mapping, multiple instances, build pipeline/packaging, installer/uninstaller.
Must expose meaningful kabl controls to host automation. Minimal proof first, then expand. Acceptance:
Ableton Live primary, REAPER secondary, real Windows environments; playback, MIDI, automation, state recall,
editor lifecycle, clean install. Cross-compilation alone is not support.

## E. Promotion (follows product work, must not delay it)
Two assets. Trailer: atmospheric, musically compelling, fast, sound + identity, broad palette, builds to big
moments, Lichen flagship. Walkthrough: first run, find a sound, change it, understand its signal path, use
composites, perform. After composites exist, redo the Lichen trailer sequence: high-level patch, inspect a
composite, change a control, back to the music. No huge flat rack. Keep useful V2 storyboard/animatic/render
work but it is not approved/final.

## Process (condensed)
Update the canonical plan (one document supersedes older roadmaps). Distinguish done+verified / exists needs
work / new / dependent / Kosta decisions / can start now. Per task: objective, scope, deliverables, deps,
acceptance, breakdown, existing code, risks, relative effort. Three initial investigations: corpus analysis
(read-only), first-run + learning design, Windows/VST3 feasibility. Then: roadmap -> first-run + learning
foundation -> composite candidates -> first composites -> migrate representative patches then corpus ->
learning progression on real composites -> Windows standalone + VST3 -> promo -> plan macOS later.
Bounded PRs, own worktree each, tests + evidence, independent review, documented result. No unapproved
musical/factory-sound changes; no irreversible product/compat decisions without Kosta; do not ask Kosta
routine technical questions; owner decisions come with alternatives, evidence, consequences, recommendation.
Keep Linux working. No unrelated DSP features. Usability and musical quality need real walkthroughs,
listening evidence and clean-install tests, not only automated tests.
