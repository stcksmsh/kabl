## B. D04 scope

### Classify before changing delivery

Create docs/runtime-controls/design.md with a source-grounded classification of existing
module parameters and cable parameters: runtime, structural/preparation, or presentation.
Cover defaults, aliases, stepped/discrete values, keyboard configuration, route amount and
bypass, and parameters used to size/precompute state. Give structural exceptions a concrete
reason. Merely naming something a parameter does not prove it can change in place.

Routine continuous sound controls and macros must use runtime delivery. Runtime-compatible
discrete controls may update in place with their existing semantics. Route amounts should
update in place where their scheduled dependency remains valid. Route creation/deletion,
or bypass when it changes scheduling/feedback dependencies, may require compilation:
document the exact boundary rather than silently changing modulation semantics.

### Identity, ordering and bounded delivery

- Key targets by stable patch/module/parameter or cable identity, not panel order, voice
  index, a reused buffer slot or a transient compiler index. Include document/generation
  lifetime so a delayed message cannot target a new sound or a reused module ID.
  Compile-time resolved slots are fine behind that validated identity.
- Apply values consistently to every relevant voice and modulated/unmodulated path.
  Preserve stored base versus modulation, taper, signed route amount, single clamp,
  stepped rounding and the existing modulation grid.
- Explicitly handle active, fading-in and pending/queued graphs. A graph compiled from
  an older snapshot must not overwrite a later edit when installed. Retired outgoing
  graphs must not regain authority. State a policy for shared targets during the fade.
- Bound queue capacity, per-callback work, outstanding ownership and retry/coalescing.
  A saturated queue must not silently lose the final intended value. Coalescing absolute
  values is allowed only where ordering remains correct; button actions, structural
  boundaries, undo and document changes are not interchangeable knob samples.
- No new callback allocation/free, logging, formatting, filesystem I/O, blocking locks
  or unbounded drain loops. Compile and destroy graphs off the audio thread. Exercise
  actual production delivery under backpressure, not only a substitute helper.
- Define requested/applied/failed state. Keep the last valid playing graph on compilation
  failure and show meaningful pending/error state without claiming an edit was applied.

### Control, document and UI ownership

Remove production mapped-CC and existing mapped-button semantics from GUI repaint polling.
CC learning stays in the UI. Delivery, pickup, mapped transport/bank/cue actions and their
ordering must continue without rendering an editor frame. This is an editor-independent
control layer, not plugin implementation or a redesign of note/event timing.

Preserve current CC behavior: channel-specific mapping, soft takeover (within 1.5/127 or
crossing), reset pickup after other value changes, one continuous CC gesture according to
the existing grouping policy, one button action per low-to-high press and the reconnect
guard. Preserve reserved sustain/panic CC handling. Inspect current source before relying
on these baseline observations; do not invent new takeover or channel routing policies.

Keep one authoritative document/history model. Audio commands do not create a second
saved patch. Mouse, CC, Undo/Redo, recipe edits and comparison restore must converge on
the same intended values. Save/reload must include accepted CC edits even when UI
notifications lag; reopening/resuming the UI cannot replay old control messages. Define
arbitration and reconciliation, including same-value edits and mapping changes. Preserve
current behavior unless evidence exposes a consequential conflict requiring Kosta.

D02 explanations remain based on the actual stored base/routes. D03 probes continue
measuring the current graph during runtime edits; accepted readings cannot survive
incompatible topology changes. Runtime parameter changes must not reset voices, note
ownership, envelope phases, sequencers, seeds, delay/reverb tails or probe windows without
a parameter-specific reason already part of the musical behavior.

### Smoothing and compatibility

Preserve existing DSP smoothing first. State where additional smoothing is needed for
the new update path, the domain, duration and reset behavior. Do not double-smooth, ramp
stepped choices through invalid states or smooth gates/triggers. A sustained fixed setting
must render like the baseline under matching seeds/state; use bit identity where applicable
and justify any numerical tolerance. Initial load at a stored value must not invent a
ramp from zero. Any necessary audible compatibility change is a product tradeoff for Kosta.

No patch-format migration unless demonstrably necessary for this scope; prefer internal
identity/control changes compatible with existing saved patches and mappings. No composites,
host automation slots, plugin framework, synthesis expansion, mono-chain optimization,
new MIDI expression, sample-accurate adapter, stream restart or broad UI redesign.
