## A. One selected signal

Deliver an opt-in inspector integrated with the existing rack/drawer and D02 navigation. Support one logical signal selection at a time; no always-on scopes on every cable.

Minimum useful coverage:
- Audio: measured level, with explicit channel and aggregation meaning.
- CV: measured value/range with correct units where metadata establishes them.
- Gate/clock: activity including short edges observed within the measurement window.
- Pitch: interpret declared pitch signals using the engine's units. Do not infer fundamental pitch from arbitrary audio.

An output jack is a sufficient primary selection surface. A cable may navigate to its source, but label this as source observation; a destination input, feedback delay or modulation reduction can differ. Do not advertise an input/effective-parameter measurement you did not implement. A small scope is optional, not a second deliverable.

Requirements:
- Identify module instance, port, channel and voice policy in the UI. A specific lane is acceptable if explicit; never label lane 0 as the whole chord. If aggregating, document the reduction and avoid averaging away activity.
- Capture at the correct schedule point before buffer reuse. Account for feedback and per-voice/global paths without changing their DSP semantics or buffer lifetime accidentally.
- Fixed bounded work/storage for the selected tap. Preallocate off the audio thread. No locks, allocation/deallocation, I/O, formatting, graph traversal of unbounded size or waiting on the UI in the new callback path.
- Bound publication rate and queue capacity; drop/coalesce telemetry on overflow. Audio continues with the inspector hidden, closed or stalled. Closing inspection disables collection work beyond minimal dispatch overhead.
- Use document/graph/selection identity or an equivalent robust mechanism. Reject stale reports after target changes, deletion/undo, patch replacement, failed compilation and overlapping swaps. Reused module IDs in a different patch must never inherit observations.
- During a fade, label the observed graph or show measurement temporarily unavailable. Do not present an individual graph tap as the crossfaded final output.
- Show unavailable, waiting and stale distinctly from zero. Include an observation interval/freshness indication. A stopped callback must not leave a believable live meter.
- Selecting, opening and closing inspection never creates a musical edit, changes save state, notes, transport, routes, parameter values or voice allocation.

Keep this separate from the D04 runtime parameter delivery project. A bounded selection/control message is allowed; a general control-path rewrite is not.

## B. Observation-led “Why no sound?”

A small in-context aid, not an automatic repair engine. Limit it to current connections, existing transport/output status and the selected measurement.

Separate:
- Graph fact: a named input is disconnected, or a bounded search found no supported cable path.
- Measurement: no gate transition or signal above a stated threshold was observed at a named tap during a stated interval.
- Possibility: a parameter or downstream stage may suppress the signal; propose where to inspect next.

Do not infer intent, audibility at speakers, missing MIDI hardware or a broken audio device from an internal zero. Pitch zero is a valid pitch; a held gate can be active without a new edge; a release tail can sound without a held key. A path search limit means unknown, not disconnected. Respect the engine's actual selected output and route semantics; do not silently mix multiple out modules or change old patches.

Demonstrate two prepared cases: a removed signal connection and a missing trigger while the relevant source is observed. Include a valid-but-quiet/stopped case to show that the tool avoids unjustified diagnosis. No invented certainty, global panic, auto-wiring, parameter reset or background scanning of every signal.

## C. One reversible comparison reference

Provide a small ordinary patch comparison mechanism usable outside recipes. One in-memory reference and the current working version are sufficient. No preset manager, persistent snapshot library or new file-format migration.

Define and expose the scope: complete patch configuration (values, graph, labels, performance mappings/layout as applicable), not DSP history or a recording.

Required action rules:
- Capture reference copies the current configuration without changing it or its undo history.
- The reference remains immutable until explicitly replaced. Reference/current controls clearly show which is heard and which can be edited.
- Working edits, including unrelated edits made during an experiment, survive returning from the reference.
- Do not silently write rack/MIDI edits into a hidden version. Either return explicitly to the working version before accepting edits, or clearly prevent editing while auditioning the reference. Document external CC/button handling too; never strand note-offs or sustain releases.
- Ordinary Save/Save As must target an unambiguous working state. Require return to the working version before saving if needed; never save an unheard hidden version without saying so.
- Closing comparison or a recipe returns to the working version and keeps its edits by default.
- An explicit Restore reference is destructive to edits made since capture: name its whole-patch scope and make it undoable as one operation, preserving prior history. Cancel changes nothing. Do not restore by rebuilding from bare state and silently erasing real undo/redo.
- Open/New/quit while comparison or a recipe is active still passes through D01 document protection for the working version. Failed load/save and cancelled dialogs preserve the working version and reference.
- References are session-local; clearly disclose that they are not saved. Successful document replacement invalidates them and all signal/help selections safely.
- Reuse established graph swap/fresh-load semantics, with explicit note/transport/tail behavior. No new hard-cut Stop or picker semantics. No claim of sample-identical live A/B: runtime phases, held notes, tails and random histories are not configuration snapshots.
- No automatic normalization or hidden gain adjustment. Compare with the same input; identify loudness differences honestly. For automated equivalence checks, use controlled events/reset/seeds.

Keep the design small. It need not switch instantly or run two complete engines concurrently. If the safe minimal implementation uses explicit restore/undo instead of an audition toggle, that is acceptable if the UI clearly presents it as restore/undo and the working edits/history remain recoverable. Record the chosen interaction in design.md.

## D. Exactly three optional listening recipes

No mandatory tutorial, unlocks, scores, runtime LLM or general curriculum engine.

1. **Pluck to pad:** attack/release on an envelope, one change at a time. Reveal the actual envelope and listen under controlled note length; explain sustain/release interaction where needed.
2. **Filter movement:** cutoff plus one existing LFO route. Reveal source, signed depth and destination; inspect the LFO, compare with route bypassed, and restore.
3. **Interlocking sequences:** two existing sequencers sharing a clock/divider. Change one pattern length and hear the relationship, reveal the relevant clock/sequence/gate path, and keep the result.

Each recipe has a small starting patch, clear intent, 3–5 short actions, explicit target identities, one audible change per action, D02 Show/Back, optional signal inspection and a final analogous unguided task. Avoid prose walls. Use existing synthesis and patches where appropriate; additive teaching patches may be created, but do not retune established factory sounds.

Opening a recipe example is an explicit document replacement through existing unsaved protection. Recipe entry never silently overwrites the current song. Do not promise restoration of a previous document merely because a recipe closes. Exit keeps the current patch and edits; explicit restore uses the stated comparison scope.

Support help dismissal, free editing, target deletion/undo and opening another sound. Missing/incompatible recipe targets produce a clear state, not guesses based only on names. If a restart would replace edited work, protect it like other document replacements.

Recipe content/resources must work in the relocatable package outside the repo. Reuse current discovery rather than introducing accounts, cloud storage or a database. The learn crate is a stub, not a requirement to build a framework.

Record actual owner/tester confusion in docs/confusions.md only when observed. Agent scripts and hypothetical confusion are not human learning evidence.

## F. Operational logging (owner-requested addition)

Kosta requested logging to make failures easier to diagnose, with production severity above DEBUG. Implement a small logging foundation in this batch; do not turn it into a monitoring platform. These diagnostic logs are separate from the musical PatchLog/op history.

- Production/release default: INFO, WARN and ERROR. DEBUG and TRACE are off by default, but available through an explicit documented runtime flag or environment setting in the same release binary. Do not compile them out so that reproducing a user failure requires a special build.
- Use a conventional Rust logging facade/subscriber and a single application initialization point. Choose the dependency after checking current official documentation and license. Do not invent a logging framework. Libraries emit events without installing a process-global logger; this also preserves future host integration.
- Logs are useful when launched from the packaged GUI without a terminal: write to a documented user-writable location, with size-based rotation and a fixed retention cap. Provide a simple way to locate/copy the log path. Choose and record modest exact byte/file limits. No uploads or remote analytics.
- Use timestamps and monotonic elapsed time, severity, subsystem, session ID, application/build identity (include commit when known; otherwise say unavailable), and relevant document/graph/selection IDs. Keep messages readable; structured fields should correlate an error, its attempted operation and outcome.
- INFO: startup/shutdown, audio backend/device and requested/actual sample rate/buffer settings, RT outcome, MIDI connection changes, document open/save completion and major state transitions.
- WARN/ERROR: failed load/compile/save/repair, device/stream faults, stalls, recorder failure, invalid diagnostic target and log-sink failure, with a useful reason and preserved-work outcome. A user cancel is not an error.
- DEBUG: bounded graph compile/swap lifecycle and durations, selection/recipe/comparison transitions and diagnostic detail useful for reproducing a fault. Routine graph rebuilds during a knob gesture are DEBUG, not an INFO flood. TRACE remains opt-in and must still be bounded.
- No per-sample, per-frame, per-note or per-knob INFO logs. Rate-limit/coalesce repeated faults and periodic health summaries, reporting counts rather than emitting an xrun line for every occurrence. Keep callback execution, arrival lateness and backend xruns separate and tied to an interval.
- No logger calls, text formatting, file I/O, locks or allocation/deallocation in the new RT path, even with DEBUG/TRACE enabled. Publish fixed-size bounded events or counters; consume/format/write on a non-audio thread. Audit the current callback/error-reporting hooks where integrating this (main.rs currently formats a stream error with eprintln). Do not assume a generic asynchronous logger makes producer-side formatting RT-safe.
- Queue full, slow/full disk, missing permissions or writer failure cannot block audio or crash the instrument. Bound buffering; count dropped diagnostic events and show a rate-limited logging-failure notice outside audio. Shutdown flush is bounded.
- Default logs contain no recorded audio, complete patch contents, note stream or typed search/rename text. Log operation IDs and errors; include paths/device names only when diagnostically needed and document that logs can contain local details.
- Preserve existing evidence hooks such as KABL_STATS_FILE, or migrate their scripts deliberately and document compatibility. Do not silently break the prior batch tooling.
- Wire the foundation into kabl-ui and the existing kabl standalone executable where they share relevant startup/audio paths. Do not rewrite unrelated module internals merely to add logging.

Evidence: release default suppresses DEBUG/TRACE; explicit override enables them; startup/audio configuration and injected load/save/audio or recorder failures correlate; rotation enforces its cap; missing/slow/full sink and full queue remain bounded. RT tests must include diagnostics enabled. Use deterministic fault hooks and distinguish them from real device/disk failures. Document exact commands and file location in README/CHECKLIST. Only broaden tests where these contracts are at risk.
