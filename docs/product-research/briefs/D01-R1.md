## R1 — Replacement confirmation can outlive the chosen name

Source: `crates/ui/src/browser.rs::dialogs`, `Dialog::SaveAs` (`taken`, name editing, Replace it), `save_as`; `crates/ui/src/library.rs::Library::save`.

At the reviewed head, after Save As reports a collision, the dialog retains the previous `taken` entry ID while the editable name can change. Replace it sends that stale ID together with the new name. Library::save uses the supplied ID as the target even when the new name is different.

Reproduction: create existing user sound A with recognizable saved content; edit another sound; Save As A to trigger the collision; change the name to an unused B; inspect/click the remaining Replace it action. The source path can replace A and rename its metadata B instead of creating B.

Required:
- Any replacement confirmation must refer unambiguously to the current requested name and exact current target.
- Editing the name invalidates stale collision/confirmation state. Re-resolve before committing a replacement; do not guess.
- Verify unused B creates a separate sound, cancel preserves A, and a deliberate replacement of A still works.
- Protect the saved bytes/identity of unrelated sounds and keep the working patch on errors.

A focused UI regression must exercise changing the field after a collision, not just test a normal collision. Add library validation where the actual API contract warrants it without breaking legitimate Save/Rename.

## R2 — Folder saves bypass failure-safe replacement

Source: `browser.rs::save` for `DocOrigin::Folder`, the advanced Save to folder button, and `crates/core/src/format.rs::save`.

Library saves stage/read back/swap. These folder paths still call the multi-file core writer directly. It writes log.jsonl before checkpoint.json/meta.toml, so a later failure can occur after saved bytes have changed. The normal Save error text nevertheless claims that nothing was overwritten.

Required:
- Bring user-facing folder Save and Save to folder under an appropriate failure-safe save path, or an equivalent implementation with accurately documented guarantees.
- Preserve the log-based format, metadata where appropriate, factory protection, and unrelated files in user-chosen directories. Do not swap away arbitrary directory contents just to reuse the library transaction helper.
- Do not introduce fsync/power-loss guarantees or multi-writer promises unless implemented.
- Preserve in-memory state, undo and unsaved indication on failure; Save-then-Open/New/Quit must not continue after a failed save.
- Deterministically inject a failure after the stage corresponding to the first authoritative-file write. Verify the previous saved sound is still available/recoverable and the UI's message is truthful. Cover successful save/reload too.
- Use a temporary fixture, not a real user sound. Permission-only tests may not work as root; choose a reliable failure injection.

No wholesale file-format migration, new browser features or deletion workflow.
