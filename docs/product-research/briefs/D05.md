## A. Recover audio without losing work

### State and visible actions

Use the existing callback-progress detector and error hand-off as inputs to explicit
audio lifecycle state. Distinguish starting, running, stalled/failed, restarting and
unavailable. An ordinary xrun is not by itself a dead stream; silence is not a device fault.
Account for startup grace, actual callback progress, UI suspension and intentional shutdown.

Provide a visible Retry/Restart audio action and a way to choose another available output
device when the selected one is unavailable. Retain requested settings and display actual
device/rate/buffer settings after negotiation. No silent switch to an arbitrary device.
Keep selection environment/session state, not musical patch identity. Avoid a broad settings
redesign. Initial device-open failure must still allow editing and saving.

Default to explicit user-initiated recovery, with one attempt at a time and bounded retry
state. Repeated clicks must not create concurrent streams or unbounded workers/queues.
Failure returns a clear actionable state; no endless automatic restart loop.
Never claim recovered merely because stream construction succeeded: observe new callback
progress and usable graph installation.

Apply the user-facing workflow to kabl-ui. Share reusable lifecycle/error primitives where
appropriate with the terminal standalone. The CLI must retain coherent failure reporting
and teardown, but a new interactive terminal device picker is outside scope.

### Lifecycle, ownership and document integrity

Keep the editor/op log, dirty/saved state, current path, mappings, comparisons, recipe and
navigation state intact. Edits accepted while audio is unavailable remain authoritative.
Recovery installs the newest valid document snapshot, not an old queued graph. If the current
document fails compilation, preserve it and the error; do not replace it with an init sound
or silently report the requested state as playing. A clearly disclosed last-valid graph may
be used if its ownership/version are sound.

Prepare/open/close streams, compile and collect retired graphs away from the audio callback.
Do not hold Core through backend teardown/open or slow file operations needed by recovery.
Keep editing/Save usable during a retry. Prove stream-before-queue teardown, recorder lifetime,
collector draining, producer replacement and control-thread shutdown across repeated attempts.
Account for basedrop ownership on repeated restarts; process-exit leaks are not harmless in
a repeated recovery loop.

No old callback may use new queues or publish current status/probe/clock reports. Give each
stream/session an identity or equivalent fence and reject stale reports. Reinitialize
delivery/feedback coherently so pending counts and revision acknowledgments cannot refer to
the retired stream.

On explicit restart, release/reset held notes, sustain and preview ownership; clear pending
launches and stale commands rather than replaying actions accumulated for a dead stream.
Retain accepted base-value edits in the document. Reset CC pickup/button state and require
fresh input; no synthetic note-on replay for physically held keys. Restart clocks stopped,
with an explicit Start action. Tell the user that live notes/tails and transport reset.
This is a stream recovery boundary, not a change to ordinary picker/preview Stop behavior.

Document which transient DSP state can survive and which must reset, especially after a
sample-rate change. Do not promise seamless audio, preserved tails or continuous transport.
Any different proposed recovery behavior that risks work or changes musical intent is a
product decision for Kosta.

Do not evade a blocked backend close by endlessly detaching workers or leaking streams.
If the backend cannot provide bounded teardown, document the limitation, keep retries
bounded and surface the blocked state. Return an unresolved access/backend constraint if
safe recovery cannot be completed; do not invent a timeout guarantee.

### Recording

A detected interruption or explicit stream restart ends the current take with an
interrupted/partial disposition. Finalize the recoverable audio and expose its path/error.
Keep existing file failure and overrun accounting. Do not concatenate audio from before and
after recovery into a supposedly continuous take, overwrite an earlier file, discard a valid
prefix, or automatically start another recording. A new take uses the recovered device's
actual sample rate and starts only on an explicit Record action.

Report observed continuity limits honestly: delayed detection cannot reconstruct missing
samples. Distinguish rendered frames, dropped recording frames and time with no callbacks.

## C. Profile before optimizing

After recovery correctness, profile the current mono-chain candidate on the post-D04 engine.
Use the same machine, rate/buffer, patches, seeds and workload for baseline/final comparisons.
Include a simple mono voice, the dense palette/composition material and mixed mono/poly
routing. Record graph/voice counts and where time is spent.

Only implement reduced-lane processing when a repeatable measured benefit and a sound
eligibility rule justify it. Otherwise deliver profiling and an explicit no-optimization
disposition; that satisfies this part. No arbitrary speedup quota and no VM-to-laptop claim.

If implemented, preserve:
- mixed source/consumer reachability and modulation, voice assignment and mono/poly changes;
- noise/random seeding, independent state, averaging/gain, effect tails and crossfade overlap;
- old patch formats and fixed-setting renders, at stated tolerances;
- dynamic topology changes and the new runtime delivery/probe contracts.

A mono chain is not simply an unvoiced chain: removing current voice averaging must not
multiply gain. Do not reduce quality, voice capability or musical behavior for speed.
No generic SIMD/engine rewrite. No claim that optimization explains the old spike or stalls.

## Acceptance and evidence

| Criterion | Evidence required |
|---|---|
| Initial failure and recoverability | Start with unavailable output; edit/save; select valid output; play without restarting app |
| Real lifecycle recovery | Real-app attempt on the actual cloud backend, including an induced backend disruption when supported; distinguish simulated faults from real device loss |
| Deterministic faults | Opt-in test hook for stream error, no callback progress, reopen failure and delayed completion; production lifecycle paths, not only the error hand-off helper |
| Repeated attempts | Repeated clicks, successive failure/success and shutdown during retry: no duplicate streams/threads, leaked graphs/queues or stale status; explicit ownership counts |
| Document/control state | Edit/save/undo while unavailable, latest values after recovery, failed compilation, stale commands, new document during retry, CC pickup and no held-note replay |
| Transport/load ordering | Deterministic pending-Load/edit/Start/second-Load cases; stopped means stopped until the correct explicit action |
| Recorder integrity | Mid-take interruption and failed reopen preserve a disclosed playable prefix; new take separate and correct rate; filesystem failures reported without lost previous takes |
| UI and callback behavior | Responsive retry/edit/save, measured Core/CC delays; allocation/deallocation and lock checks on changed production paths |
| Inspection/logging | Old-stream measurements expire; state transitions/settings/errors/counts logged off audio thread with session identity; INFO default, bounded logs |
| Efficiency | Comparable profiling; justified optimization with sound/state/gain regressions, or documented deferral |
| Regression/delivery | Workspace tests and clippy; final release package outside checkout, fault/retry/play/quit smoke test |
| Owner | Laptop 48 kHz/256, real controller/device loss/reconnect, recording and listening checklist left pending |

Test fault hooks must be explicit opt-in and inactive by default, not normal product controls.
A synthetic callback stall is not proof of an actual ALSA hang's root cause or recoverability.
If a real backend disruption cannot be produced, say exactly what was exercised and leave
hardware evidence pending. Do not turn off measurements or discard stalled runs.

Use 48 kHz/256 where supported. Report callback execution, arrival lateness and xruns
separately, plus run duration/count and recovery time. Label failed/censored runs. Include
at least one focused real-app walkthrough with audio and necessary screenshots at both
1440x900/1280x800 and light/dark themes. Record on the final product head; refresh affected
evidence after fixes or justify exact unchanged paths. Old D04 performance is historical.
