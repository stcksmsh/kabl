## Outcome

A musician opens a factory sound, changes an existing performance control, sees exactly which parameter or routes it controls, and reaches those controls in the rack without losing their place or their sound.

This is a focused explanation/navigation layer on the existing instrument, not a new synth UI. Preserve rack character, themes, cable modes and the single patch/parameter state. Modular beginners should learn through editing a useful sound.

## Scope

### A. Performance controls reveal their real targets

- Add an explicit discoverable explanation/reveal action for existing pinned parameters and macro controls.
- A direct pin reveals its original module parameter.
- A macro lists actual outgoing destinations for that specific macro output: module label/kind, parameter or signal port, route amount/direction and bypass status as applicable.
- Use current graph identities, not cached display names or an authored list that drifts. Handle no destinations, several destinations, duplicated names, deleted routes/modules and undo.
- Clicking a target brings it into view, reveals an off-face control when needed and uses existing inspection/highlight mechanisms. Clearly show which target is selected and preserve a way back to the originating control.
- Navigation/inspection does not change audio, the saved patch or musical undo. If current permanent face customization is the only reveal route, add transient inspection rather than silently saving a new face.
- Keep both full rack editing and Perform available. Do not force a tutorial or a new editing mode.

### B. Contextual module and parameter help

- Consume existing ModuleInfo.explain for module descriptions after checking its wording against actual behavior.
- Explain parameter purpose, units, range and relevant stepped choices using existing metadata/formatters. Add focused authored help where raw internal names are insufficient.
- Cover the public controls of the current factory voices/pieces, including pinned controls, keyboard settings, macro depth, envelope attack/release, filter cutoff/resonance and sequence/clock controls. Reuse per-module/parameter help, not a prose copy for every patch instance.
- Show the musical label and underlying parameter identity together when useful. Never assume that an arbitrary knob named Brightness has a particular function.
- Do not display presentation bookkeeping fields (pin.*, face.*, mapping encodings) as sound-design controls.
- Keep explanatory text concise and opt-in/contextual. Common controls should remain reachable with help closed.

### C. Base value, modulation and external control

- Explain stored base value versus configured modulation contribution, sign and bypass. Preserve current taper-space math, clamping and smoothing.
- Display configured range/depth accurately. Do not pretend to display instantaneous effective DSP values without telemetry; that is not this batch.
- Existing MIDI CC pickup writes the same base value. Help should distinguish that mapping from a modulation source where available.
- There is no host automation implementation yet. Do not add D04 control delivery or D08 automation while explaining current behavior.
- Any overview of a patch's signal path must derive from current graph connections, remain bounded for large/cyclic graphs, and distinguish authored intent from graph facts. A concise connected-route view is sufficient; do not build a separate graph editor or guess why silence occurs.

### D. Layout and behavior

- Use the existing A-light/A-dark language. Fit at 1440×900 and 1280×800 with browser/Perform/routing states exercised.
- Prefer reusing the current drawer/inspector over adding several permanent panels. Preserve user's chosen cable mode and module positions.
- Keep search/text-field focus separate from global shortcuts. Help and return navigation must not trigger preview, transport or parameter edits.
- Cover label changes, module removal, undo/redo and patch replacement with help open; invalidate references safely.
- Do not modify D01 audition picker, Stop/tails, save dialogs, serialization or library identity.

## Non-goals

No composites or module-preset browser, panel designer, DSP changes, new synthesis modules, runtime LLM, lessons, signal telemetry, why-no-sound diagnostics, A/B framework, plugin or runtime-control redesign. Do not retune factory sound values or change macro routes just to make explanations simpler. Authored help/labels are allowed; preserve musical state.

## Acceptance

| Criterion | Required evidence |
|---|---|
| Direct pin -> parameter | Real-app action reaches the exact underlying control, including a currently hidden/off-face control |
| Macro -> multiple destinations | Show source, signed/bypassed routes, reveal each; remove/change a route and undo with help updating correctly |
| Honest explanation | No route yields a clear empty state; duplicated labels remain distinguishable; unavailable instantaneous values are not fabricated |
| One state | Edits from Perform and rack agree; undo/save/reload retain the same values and routes; opening help alone does not dirty the document |
| Base/modulation distinction | Demonstrate a modulated control and explain base, depth/direction and bypass with correct units/formatting |
| Factory help coverage | A compact coverage table for public factory controls; meaningful specific help or justified fallback, not a test-count target |
| Navigation/focus | Return to source, patch replacement, module deletion, text entry and Escape behave predictably without changing sound |
| Layout | Real screenshots in both sizes/themes and a short audible walkthrough showing the complete workflow |
| Regression | Focused meaningful interaction/state tests plus cargo test --workspace and cargo clippy --workspace --all-targets on the reported head |
| Final integration | D01-R1 incorporated, combined state tested and rechecked by reviewer before merge-ready claim |

The novice task (find the control that makes a pad brighter/slower, explain the actual destination without assistance) remains an owner/user observation. Scripted clicks are software evidence, not proof of beginner ease.
