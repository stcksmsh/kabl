# D05 audio recovery design

Base: `e951b2535d817bc7c21872cd0e46e815d35747ac` (fetched `origin/master`, 2026-09-27). The implementation is on `codex/d05-audio-recovery` for owner review.

## Lifecycle and ownership

The UI reports Starting, Running, Stalled, Failed, Restarting or Unavailable. Callback count has a three-second startup grace and a 1.5-second subsequent stall window; xruns alone do not fail. A non-xrun error sticks. The control thread observes progress even without an editor frame and closes the callback gate on failure. Reopening is explicit and single-flight; repeated clicks cannot spawn more workers. The selected output is an exact enumerated index and name, checked again on open. The default selection is explicitly "System default". Requested rate/buffer remain in the session request, and the negotiated rate, channel count and requested buffer are shown in the status tooltip. The backend does not expose a verified actual callback buffer during construction; telemetry records min/max frames delivered.

`AudioHost` owns the stream before consumers and collector; the retry worker closes the old stream, collects retired graphs, drops old queues, optionally waits for an opt-in delay, and opens a muted new stream. The UI replaces the old producer with a no-audio delivery, fences stale feedback and CC arrivals from before Retry, clears its latency waiters and snapshots the *current* editor document only when the new stream has opened. The new delivery compiles it as a fresh stopped graph. Until callback progress and graph revision acknowledgment after the fade, the gate remains closed. An edit in the confirmation frame resets the gate to the newest revision. A compile failure keeps the document and error visible and does not report Running. Failed opens leave the editor/save usable. On a successful recovery, notes become available only after the new graph is installed. Inspector report lineage and command token reset per session while retaining the signal selection. Session-specific stream callbacks own only their own queues, counters and gate, so retired status cannot publish into the new session.

Retry releases old notes/sustain/preview and clears pending launches/transport, clock/step reports and CC pickup; no physical key replay occurs. Fresh graphs stop clocks, including a Load replaced by an edit during a fade. An explicit Start is required. DSP delay/envelope/tail, voice and random state from the old stream are discarded; rates may differ, so no state continuity is promised. A transport command queued behind a pending fresh Load addresses that new graph, and Toggle considers its stopped intent. At most 64 waiting actions are retained by ordinary delivery; offline actions are refused and counted. The old stream is closed before queue/collector teardown. The control pump stops and joins on app drop; if the backend's stream drop blocks, the one worker remains owned and Retry stays disabled rather than detaching endless workers. There is no bounded close guarantee from the backend.

## Recording

Failure or explicit retry ends an active take through `stop_interrupted` on a writer thread. Its playable prefix and dropped-frame count are reported as an interrupted/partial outcome, with the file path or error. The old recorder is not reused; a new recorder uses the recovered stream's negotiated sample rate, inherits the chosen folder and last result, and requires a new Record action. This does not invent samples for the interval without callbacks. The take duration is based on frames rendered at the original recorder rate, not the later device rate.

## Realtime and lock boundary

The audio callback owns `PatchEngine`, drains bounded controls, renders, records into an existing ring, reports counters, and never takes `Core`. Stream teardown/open and retired-graph collection happen outside the callback. The editor frame and CC pump still share `Core`; recovery's backend close/open and recording file finalization are outside that lock, but document compile at retry completion and the older synchronous Save/Open browser paths remain inside it. Thus a delayed filesystem operation can delay mapped CCs and editor frames. This is an unresolved D05 acceptance gap pending a transactional asynchronous browser operation and measurement; a synthetic delay would not prove it fixed. The callback's D04 allocation test covers its drain/process helper, not the whole production callback body; the new lifecycle is outside the callback except gate checks and atomic telemetry. The accepted D03-R1 backend error overflow exception remains narrow.

## Fault switches (test only)

`KABL_AUDIO_FAULT=stall|error` with `KABL_AUDIO_FAULT_AFTER=N` induces a callback stall or non-xrun error after N invocations on the initial stream. `KABL_AUDIO_FAIL_REOPEN_ATTEMPTS=N` fails the first N explicit retries. `KABL_AUDIO_RETRY_DELAY_MS=N` delays completion (capped at 5000 ms) after old teardown. These are opt-in environment switches, absent from normal controls. The ALSA null PCM test uses a real backend stream but cannot establish physical unplug/reconnect behavior or the cause of historical cloud stalls.

## Mono profiling decision

`crates/engine/examples/mono_profile.rs` measures four 64-frame blocks per callback, 48 kHz, eight voices, alternating note bursts and silence, with a warmup run and four measured runs for Init Keyboard, Sound Palette and Composition. It reports graph and voice-instance counts. There is no reduced-lane change: voice-averaging/gain, modulation, state and crossfade compatibility require a reachability rule, and no isolated repeatable speedup for an eligible graph has been measured. Existing processing is retained.
